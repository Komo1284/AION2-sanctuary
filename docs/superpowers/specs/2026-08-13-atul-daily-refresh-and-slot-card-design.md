# 전투력 매일 갱신 + 슬롯 카드 표기 일관화 — 설계

작성일: 2026-08-13

## 배경

포스 편성 도구가 배포된 뒤 두 가지 요청이 들어왔다.

**하나.** 등록된 캐릭터의 전투력(아툴 점수)이 등록 시점에 한 번만 조회되고 그 뒤로 갱신되지 않는다.
사람들이 장비를 맞추면 전투력이 오르는데 화면은 옛날 숫자를 계속 보여준다. 매일 한 번 자동으로
다시 조회해야 한다.

**둘.** 슬롯 카드의 둘째 줄이 캐릭터 종류에 따라 다른 뜻을 갖는다. 본캐를 넣으면 직업이 나오고
부캐를 넣으면 소유자 본캐명이 나온다. 같은 자리가 다른 정보를 담으니 읽는 사람이 매번 판단해야
한다. 그리고 전투력은 카드에 아예 없어서 포스의 화력을 보려면 대기창을 따로 봐야 한다.

## 발견된 기존 문제

설계 중 서버에서 두 가지를 확인했다. 이번 작업에서 함께 처리한다.

**끊긴 크론이 매분 실패하고 있다.** root 크론탭에 다음 항목이 남아 있다:

```
* * * * * /usr/bin/php /var/www/html/sanctuary/cron/update_atul.php >> /var/log/sanctuary_atul_update.log 2>&1
```

`cron/` 디렉터리는 앞선 개편(Task 8)에서 삭제됐다. 그 뒤로 이 작업은 매분 `Could not open input
file` 을 뱉었고 로그가 **13MB · 17만 줄**까지 불어났다. 원래 주기가 하루 1회가 아니라 **매분**이었다는
점도 함께 기록해둔다 — 외부 API를 분당 한 번씩 두드리고 있었다.

**타임스탬프 타임존이 섞여 있다.** 서버 시스템 타임존은 `Etc/UTC` 이고 PHP CLI 기본값도 UTC다.
반면 `index.php` 는 `date_default_timezone_set('Asia/Seoul')` 을 호출한다. 그래서
`force/store.php` 의 `date('Y-m-d H:i:s')` 가 만드는 `atul_updated_at` 값이 **웹 요청에서는 KST,
CLI에서는 UTC** 로 저장된다. 지금은 이 컬럼을 화면에 쓰지 않아 드러나지 않지만, 새로 만드는 CLI
스크립트도 같은 함정에 빠지므로 명시적으로 맞춘다.

## 결정 사항

| 항목 | 결정 |
|---|---|
| 갱신 방식 | 크론 (사용자가 크론탭 수정에 명시적으로 동의함) |
| 갱신 주기 | 하루 1회, **한국시간 05:00** = 크론탭 `0 20 * * *` (서버가 UTC이므로) |
| 조회 실패 시 | **기존 값을 유지한다.** 절대 덮어쓰거나 비우지 않는다 |
| 임시 캐릭터 | 조회를 **시도하지 않는다** (외부 API에 없는 이름) |
| revision | 캐릭터마다가 아니라 실행 끝에 **한 번만** 증가 |
| 카드 레이아웃 | 2줄 고정. 1줄 = 이름(+⭐ 또는 소유자), 2줄 = 클래스 · 전투력 |
| 카드 높이 | 46px 유지 (한 화면에 보이는 포스 수를 줄이지 않는다) |

## 비목표

- 갱신 이력 보관. 현재 값만 덮어쓴다.
- 갱신 실패 알림. 로그에만 남긴다.
- 사이트에서 누르는 「전체 갱신」 버튼. 캐릭터 단위 `atul.refresh` 는 이미 있다.
- `atul_updated_at` 을 화면에 표시하는 것. 저장만 하고 쓰지 않는다(기존과 동일).

## 1. 슬롯 카드 표기

### 화면

```
1파티  ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
       │ ⭐컹용        │ │ 소월령   컹용 │ │ 코모부캐1  코모│
       │ 검성 · 41,200 │ │ 치유성 · 38,000│ │ 미정          │
       └──────────────┘ └──────────────┘ └──────────────┘
          본캐            부캐            임시 캐릭터
```

**1줄** — 왼쪽에 캐릭명. 본캐면 이름 앞에 `⭐`. 오른쪽 끝에 소유자 본캐명(부캐·임시 캐릭터만).
**2줄** — 항상 `클래스 · 전투력`.

카드 전체가 왼쪽 정렬이다(현재는 가운데 정렬). 1줄은 `justify-content: space-between` 으로
이름과 소유자를 양끝에 붙인다.

### 빈 값 처리

"아직 못 가져왔다"와 "임시라서 없다"가 구분되어야 한다.

| 상태 | 1줄 | 2줄 |
|---|---|---|
| 본캐 | `⭐컹용` | `검성 · 41,200` |
| 부캐 | `소월령` … `컹용` | `치유성 · 38,000` |
| 임시 캐릭터 | `코모부캐1` … `코모` | `미정` |
| 조회 실패한 실제 캐릭터 | 위와 동일 | `직업? · —` |

전투력은 `toLocaleString()` 으로 천 단위를 구분한다. 실제 값이 6~7자리(예: `867,349`)라 구분이
없으면 읽기 어렵다.

`atul` 이 `null` 이면 `—`, `class` 가 빈 문자열이면 `직업?` 이다. **`atul === 0` 도 `—` 로 나온다**
— 기존 코드가 이미 그렇게 동작하고 실제로 0점 캐릭터가 없어 그대로 둔다.

### DOM 구조

기존 드래그앤드롭이 `.fc-slot[data-slot-id]` 와 `.fc-slot.is-filled[data-character-id]` 에
의존한다. 이 계약은 그대로 두고 **안쪽 구조만** 바꾼다.

```html
<div class="fc-slot is-filled" data-slot-id="…" data-character-id="…" draggable="true">
  <div class="fc-slot-top">
    <span class="fc-slot-name">⭐컹용</span>
    <span class="fc-slot-owner">컹용</span>   <!-- 부캐·임시만 -->
  </div>
  <div class="fc-slot-meta">검성 · 41,200</div>
  <button class="fc-slot-x" data-slot-id="…">×</button>
</div>
```

`.fc-slot-owner` 는 기존에도 있던 클래스명이지만 **의미가 바뀐다** — 예전엔 "본캐면 직업, 부캐면
소유자"였고 이제는 "소유자 전용"이다. `.fc-slot-meta` 가 새로 생긴다.

`is-dup`(중복 경고 빨간 테두리)와 `is-placeholder`(회색 점선) 클래스는 그대로 유지한다.

## 2. 매일 갱신 스크립트

### 파일

`force/cron_refresh_atul.php` — 서버에서 `php force/cron_refresh_atul.php` 로 도는 CLI 전용
스크립트다. 웹으로 접근되면 안 된다.

기존 구조의 계층 분리를 따른다: `atul.php`(외부 조회)와 `store.php`(DB)를 조합만 하고, 자기가
SQL을 새로 쓰지 않는다.

### 동작

1. `date_default_timezone_set('Asia/Seoul')` — CLI 기본값이 UTC라 명시하지 않으면 웹과 다른
   타임스탬프가 저장된다.
2. `is_placeholder = 0` 인 캐릭터 전부를 `id` 순으로 읽는다.
3. 각각에 `fc_atul_lookup($name)` 을 호출한다.
   - **성공**: `char_class`, `atul_score`, `item_level`, `atul_updated_at` 갱신
   - **실패(`null`)**: 아무것도 쓰지 않고 다음으로 넘어간다
4. 호출 사이에 **300ms** 쉰다. 외부 API를 몰아치지 않기 위해서다.
5. 끝에 `fc_bump_revision()` 을 **한 번만** 호출한다.
6. 한 줄 요약을 출력한다: `[2026-08-13 05:00:12] 아툴 갱신 — 성공 58 / 실패 2 / 건너뜀 3 (12.4초)`

### 실패 정책의 근거

조회 실패는 흔하다. 외부 API 점검, 네트워크 순단, 캐릭터 개명, 서버 이전 등으로 언제든 `null` 이
돌아온다. 그때 기존 값을 지우면 **하루 만에 전체 명단의 전투력이 날아갈 수 있다.** 반대로 유지하면
최악의 경우 값이 조금 낡을 뿐이다. 실패 쪽으로 기울어야 할 방향이 명확하다.

### revision을 한 번만 올리는 이유

`fc_update_character()` 는 호출마다 revision을 올린다. 60명을 갱신하면 60번 올라가고, 그 사이
접속해 있는 사람의 브라우저는 10초 폴링에서 변경을 감지해 화면을 다시 그린다. 결과는 같지만
불필요하다. 갱신을 끝낸 뒤 한 번만 올려서 **한 번의 재렌더로 전부 반영**되게 한다.

이를 위해 `store.php` 에 revision을 올리지 않는 내부 갱신 함수를 하나 둔다. 기존
`fc_update_character()` 의 동작은 바꾸지 않는다 — 다른 호출자가 전부 revision 증가를 기대하고 있다.

### 테스트 가능성

`fc_atul_lookup` 을 직접 부르면 테스트가 외부 API에 묶인다. 갱신 로직을 **조회 함수를 인자로 받는
함수**로 분리해서, 테스트가 가짜 조회를 넣을 수 있게 한다. CLI 진입점만 실제 `fc_atul_lookup` 을
넘긴다. 프로젝트의 기존 패턴(`fc_create_player($pdo, $name, $subs, $lookup)`)과 같다.

## 3. 크론탭 정리

**변경 전**
```
* * * * * /usr/bin/php /var/www/html/sanctuary/cron/update_atul.php >> /var/log/sanctuary_atul_update.log 2>&1
```

**변경 후**
```
0 20 * * * /usr/bin/php /var/www/html/sanctuary/force/cron_refresh_atul.php >> /var/log/sanctuary_atul_update.log 2>&1
```

`0 20` UTC = **한국시간 05:00**. 서버 타임존이 `Etc/UTC` 임을 확인했다.

기존 13MB 로그는 비운다(`: > /var/log/sanctuary_atul_update.log`). 앞으로는 하루 한 줄이므로
1년에 365줄 정도만 쌓인다 — 로테이션이 필요 없다.

**이 작업은 `/var/www/html/sanctuary/` 밖을 건드린다.** CLAUDE.md의 경로 제약에 대한 예외이며,
사용자가 명시적으로 동의했다. root 크론탭의 **이 한 줄과 이 로그 파일 외에는 아무것도 건드리지
않는다** — 다른 크론 항목(`certbot`, `eztake-usage-sync` 등)은 그대로 둔다.

## 4. 검증

### 자동 테스트

`force/test_api.php` 에 추가한다. 가짜 조회 함수를 주입하므로 외부 API에 의존하지 않는다.

1. 조회 성공 시 `atul_score`, `item_level`, `char_class`, `atul_updated_at` 이 갱신된다
2. **조회 실패 시 기존 값이 그대로 남는다** — 이 스펙에서 가장 중요한 단언이다
3. 임시 캐릭터는 조회 함수가 **호출되지 않는다** (호출 횟수를 세어 확인)
4. 전체 실행 후 revision이 **정확히 1** 증가한다
5. 요약 결과(성공/실패/건너뜀 개수)가 실제와 맞는다

테스트 데이터는 기존 관례대로 `zzTest_` 접두사를 쓰고 스스로 정리한다.

### 수동 확인

- 서버에서 `php force/cron_refresh_atul.php` 를 실제 캐릭터로 한 번 돌려 전투력이 갱신되는지
- 크론탭 변경 후 `crontab -l` 로 항목이 하나만 바뀌었는지, 다른 항목이 온전한지
- 브라우저로 카드 표기를 눈으로 확인 — 본캐 ⭐, 부캐 소유자명, 임시 `미정`, 전투력 천 단위 구분
- 드래그앤드롭·중복 경고·슬롯 교체가 카드 구조 변경으로 깨지지 않았는지
